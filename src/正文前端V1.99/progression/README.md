# 累计经验与等级

本目录是 V1.99 成长规则的唯一主源。当前版本 `staged-50-70-90-v1`，阈值全部定义在 `experience.ts` 的
`EXPERIENCE_THRESHOLDS` 中。新增任务、打工、战斗和道具奖励均应读取这里，不再建立另一份等级公式。

| 到达等级 | 累计经验 |
| -------- | -------: |
| 1        |        0 |
| 50       |    6,025 |
| 70       |   11,675 |
| 80       |   17,025 |
| 90       |   25,375 |
| 100      |   39,875 |

1–50 级基础成长，50–70 级逐渐放缓，70–90 级明显增加成本，90–100 级冲顶。等级由满足 `阈值 <= 累计经验`
的最高等级决定；升级不扣累计经验。难度不改变阈值，也不再额外降低经验收入。

## 数据与结算

- `stat_data.角色基础.经验值`：本地真实累计经验的显示副本，保留两位小数，达到 39,875 后封顶。直接改这里不会改变真实经验。
- `stat_data.角色基础._等级`：脚本根据经验派生的缓存。AI 不写等级。
- `MvuData._amamiState.experience`：结算版本、本地真实经验 `settledExperience` 和已发奖等级。跟随每个消息/swipe 保存，位于 `stat_data`
  外，不属于 AI 可更新的人设变量。
- `stat_data.角色基础._段位`：独立保留，不再由等级计算。

`settleExperience(data, previous?)`
会把本地真实经验同步到显示变量、计算等级并发放尚未发过的升级奖励。它不把显示变量与记录的差值当作收入。前端明确奖励经 `grantExperience` 入账、消耗经 `deductExperience` 扣除；重复运行不会重复发奖。

AI 的经验请求由 `ai-experience.ts` 从本轮 MVU 已解析的经验操作中提取，合并后每条回复最终最多入账100经验，包含天赋加成；1000、10000及多条操作均不能超过上限。直接改显示总数、没有对应解析操作、或 AI 写等级，都不会修改本地真实经验。JSONPatch校对共用相同上限；前端任务、战斗、商店等明确奖励不受AI上限影响。

每级基础自由属性点已减半为 `floor(潜力 / 2) / 2`，保留0.5点余额；“天赋异秉”额外1点完整保留。技能点仍为 `floor(潜力)`，“快速学习”额外1点不变。已发放的旧自由点和历史加点保留，不追溯砍半；新规则从接入后的实际升级开始。

固定属性成长已接入 `settleExperience`，并独立维护 `MvuData._amamiState.attributeGrowth`（位于 `stat_data` 外）。按当前等级、当前潜力重算应有累计成长，与账本中的已计入成长比较，仅补扣差额；自由点余额、手动投入及其他加值不参与是否达标的判断。10.0潜力顶点及5.0–10.0完整51档见文末。

用户已明确新增成长的边界：只覆盖最大耐力、最大快感、魅力、幸运四项；排除性斗力、忍耐力、闪避和暴击。现有性斗力、忍耐力的等级×潜力公式沿用。四项新增成长受当前潜力影响，系数精度0.1；此前八项/六项候选和约28%的平均增益结论均不适用于当前方案。

“经验丰富”保留旧天赋 ID，但效果改为新增经验 +25%，由结算层应用一次。调用方只传基础经验。该效果等效于旧版升级需求降低20%，全体角色仍共用固定门槛。

扣除经验只消耗当前级进度，不掉级、不回收已发点数。满级后新增溢出经验按原有比例 `1经验 = 200天海信用点`
转换；经验字段保持39,875，不清零。

## 新功能接入

模型函数只修改传入数据，持久化应放在现有 MVU 事务内。例如内嵌手机的任务/打工结算：

```ts
import { grantExperience, getExperienceRewardBudget } from '../../../shared/experience';
import { updateLatestMvuData } from '../../../shared/mvuStore';

// 内容设计为70级，基础奖励相当于该级升级成本的25%，即100经验。
// 使用内容的设计等级，不跟随玩家等级自动抬价。
const reward = getExperienceRewardBudget(70, 0.25);
await updateLatestMvuData(data => {
  grantExperience(data, reward);
});
```

- `getLevelThreshold(level)`：到达指定级别的累计门槛。
- `getLevelExperienceCost(level)`：该级升下一级的成本；100级返回0。
- `getExperienceBetweenLevels(from, to)`：一个成长阶段的经验预算。
- `getExperienceRewardBudget(contentLevel, fractionOfLevel)`：按内容设计等级计算基础奖励预算；100级内容参照99→100的成本。
- `getExperienceProgress(total)`：等级、本级进度、下级门槛、剩余经验、百分比及满级状态。
- `grantExperience(data, amount)` / `deductExperience(data, amount)`：统一发放/扣除入口。
- `initializeExperience(data, initialLevel)`：开局与人物预设初始化；设定对应门槛，不追溯发放此前等级的奖励。

这里提供奖励预算工具，不预先替新打工或新任务决定收益。现有转盘的基础经验数额保留；以后调整来源数值时，使用内容耗时、完成次数与上述升级成本一起设计。

## 属性成长：已实现的顶点与潜力衰减

实现主源为 `attribute-growth.ts`，由经验结算统一调用。已按用户确认的10.0潜力顶点实现；低潜力档按等比例衰减展开，潜力范围5.0–10.0、步长0.1，共51档。开局、维护脚本、手机写回、AI变量更新/校对、战斗提交均连接同一结算。

### 生效范围与公式

- 新增固定成长仅覆盖最大耐力、最大快感、魅力、幸运。性斗力、忍耐力、闪避、暴击不加入此成长。
- 10.0潜力系数分别为12.0、12.0、3.0、3.0，累计成长乘数为0.8。表中系数尚未乘0.8。
- 设当前潜力为P，最大耐力/最大快感系数为 `round1(12.0 × P / 10)`，魅力/幸运系数为 `round1(3.0 × P / 10)`。
- `round1` 为四舍五入到一位小数；例如9.5潜力的魅力/幸运系数2.85取为2.9。实现时可将潜力与系数换算为整数十分位计算，避免浮点半舍入歧义。
- 各项额外累计成长 = `(当前等级 - 1) × 对应潜力档系数 × 0.8`。系数已包含潜力缩放，累计时不得再次乘P/10。
- 潜力每下降0.1，未取整的系数缩放比例下降顶点的1%；5.0潜力保留顶点50%。系数取一位小数后，小项会出现相邻档位重复，但四项合计等效点在51档间严格递减。
- 每项系数分别保存，当前最大耐力与最大快感相等、魅力与幸运相等；并不合并为一个属性字段。魅力/幸运在取整前保持资源系数的1/4，取整后不保证每档精确为1/4。
- 用户最新决定允许多退少补：使用当前等级与当前潜力计算应有累计成长，与独立账本中的已计入成长相减，差额可正可负；写回后更新已计入值。无须逐级记录历史潜力，重复结算差额为0。手动加点与其他来源加值不计入这一差额。
- 1级固定成长为0；1→100共99次升级。按累计公式计算、字段保留百分位，不逐级舍入；系数为0.1精度，乘0.8后保留百分位。下表等效预算保留两位小数用于比较。
- 固定成长与减半后保留的自由点并存。原自由点可购买的属性范围不因固定成长排除闪避/暴击而改变；技能点规则沿用。天赋异秉额外1点不减半，任务/道具属性点奖励也不减半。
- 最大耐力/最大快感的成长只描述上限，不自动等同于补满当前资源。

### 预算口径

现有兑换比例：1属性点可换最大耐力或最大快感10点，或魅力或幸运2点。因此100级固定成长等效点为：

`99 × 0.8 × (最大耐力系数 / 10 + 最大快感系数 / 10 + 魅力系数 / 2 + 幸运系数 / 2)`

10.0潜力时，额外最大耐力/最大快感各950.4，额外魅力/幸运各237.6，合计427.68等效点。自由点保留每级2.5，99次升级共247.5点；合计675.18等效点。旧版每级5点，99次升级为495点，因此当前总量是旧版136.4%，增幅36.4%。不含初始属性、天赋额外点、装备或剧情奖励，也不代表实战胜率增幅。

2026-11-11 用户要求自由分配点不变、降低固定成长，将同口径总量控制在旧版130%～140%左右，最多接受150%。因此把乘数从1.5降至0.8。旧1.5方案的1049.4等效点（旧版212%）已废弃；存档按账本中的旧 appliedGrowth 与新目标的差额回收固定成长，保留手动加点及自由点余额。

### 独立加点账本：已接入

用户已接受由脚本持久化记录各属性投入点数，并明确目的：排除手动加点对固定成长补扣判断的影响，避免总属性达到成长目标时误判为已经发足。使用酒馆助手原生变量接口，无须将账本写入MVU的 `stat_data` 或让AI维护。

- 权威账本存入消息楼层数据的独立字段（与 `stat_data` 并列），显式保存/继承当前消息分支快照。聊天变量可用于索引，内存缓存仅用于读取加速；不把几种存储各自作为独立真值。
- 记录六项“手动投入属性点”：魅力、幸运、闪避、暴击、最大耐力、最大快感。数字单位是消耗的点数，例如耐力投入20点对应耐力上限+200，不记录为投入200点。
- 另记四项“已计入固定成长”，供潜力/等级变化时按新应有值减旧已计入值，多退少补。固定成长不增加手动投入计数。
- `awardedLevelPoints`单独累计接入后实际发放的升级自由点；任务/道具奖励仅增加自由点余额，不修改此累计或固定成长账目。潜力变化仅多退少补固定成长，不回收已花自由点或重算历史自由点。
- fork手机、本体与测试版三个加点入口统一调用 `allocateAttributePoints`，同时扣自由点、增加对应属性并记账，再将整份楼层数据一并保存。任何新增加点入口也应调用此方法；只观察最终属性差值无法可靠区分加点、道具、剧情和成长。
- 账本随消息/重roll分支数据保存，AI更新与校对在元数据缺失时从该分支前态继承。战斗提交同步经验游标，对属性和账本按来源合并差额；战斗期间手机加点不会被旧战斗面板覆盖。刷新战斗玩家数据时同时同步账本。
- 脚本变量亦可持久化，但默认绑定脚本而不是当前聊天，需另行划分存档。纯JS内存在刷新后丢失；localStorage/IndexedDB属于当前浏览器站点，清站点数据或换设备不会自动随聊天迁移。
- 新开局或接入后的加点可以准确记录。旧存档如果没有历史加点流水，不能仅凭当前面板唯一还原各属性过去的投入；应保存接入基线并从此记账，不能把未知历史当作从未加点。
- 旧档首次接入将当前各项属性存为 `baseline`，`origin` 标记为 `legacy-baseline`；其上完整补入当前等级/潜力的固定成长。历史自由点不扣除。新开局标记 `new-character`，指定初始等级获得相应固定成长，但不补发历史自由/技能点。
- `getAttributeGrowthTargets(level, potential)`供其他模块查询四项应有累计成长；`getAttributeGrowthState(data)`读取账本；`allocateAttributePoints(data, path, cost)`执行加点。纯计算模块只操作传入数据，不依赖MVU全局对象或浏览器缓存。

### 加点不抵扣固定成长：结算判据

只比较本属性的“应有固定成长”与“已计入固定成长”，绝不能拿总属性面板与固定成长目标比较，也不能仅从总属性减去手动加点就假定剩余全部是固定成长（还可能包含初始值、道具与其他永久增减）。

1. 读取当前等级L与当前潜力P；按上表计算 `targetGrowth = (L - 1) × coefficient(P) × 0.8`。系数已经包含潜力，不能再乘一次P。
2. 读取独立账本本属性的 `appliedGrowth`，计算 `delta = targetGrowth - appliedGrowth`。
3. 对原基础属性字段应用delta，同时将账本 `appliedGrowth` 更新为targetGrowth；正数补足，负数扣回。手动投入点数与对应加值保持原样。
4. 每次手动加点只增加手动投入记录与相应基础字段，不增加appliedGrowth；装备/状态仍沿用既有派生流程。
5. 再次处理相同等级和潜力时delta为0；楼层/消息分支恢复时属性和账本一起恢复。

示例（仅说明结算，不代表某个指定等级）：初始耐力100、手动投入20属性点带来200耐力、已经计入成长800，合计1100。新的应有固定成长为900时，应补 `900 - 800 = 100`，基础耐力变为1200；不能因为1100大于900就跳过，也不能扣走手动加点。若应有成长改为700，则仅回收原成长中的100。

## 配套清理：跟随MVU，仅清理本模块新增账本

`retention.ts` 只在1.99启用时运行，绑定当时角色卡的avatar标识；切到其他卡不执行。清理范围为该卡当前聊天，读取所有消息分支，不改正文、swipe文本或其他脚本的变量。

依据[MVU清理源码](https://github.com/MagicalAstrogy/MagVarUpdate/blob/beta/src/function/cleanup/cleanup_variables.ts)，MVU只删除自己的 `initialized_lorebooks/stat_data/display_data/delta_data/schema`，保留其他根字段。我们因此跟随其实际清理结果，不另设一套保留楼层数，也不修改MVU全局设置：

- 仍有 `stat_data` 的分支、0楼及 `snapshot: true` 的快照保留账本。
- MVU已删除 `stat_data` 的旧分支，四份脚本账本统一改为 `_amamiState.delta` 差量，恢复时还原对应楼层和 swipe 的完整树。
- 如果MVU关闭清理，或设置保留20楼与定期快照，我们也跟随这一结果；并非硬性只留5份。消息接收、变量更新、切聊天等事件后检查一次，运行初始化时也补清理已有残留。
- 新版差量保留经验、成长及手动加点记录，恢复后不重复发奖。旧版已删除经验明细、仅剩清理标记且没有可恢复分支的楼层不自动建立经验基线；已删除的历史投入无法追溯，不伪造明细。
- 存储结构与迁移入口见 `../state/README.md`。
